# Effective-universality diagnosis, verifier and database checkpoint — 2026-08-05

Status: private local development evidence. This does not establish effective universality,
customer compatibility, production readiness or a 99.9% result.

## Result

The second checkpoint extends the foundation in five directions:

1. **Trusted ordinary-goal preparation.** A model-compatible planner may select only one
   predeclared customer workflow key. Trusted customer-local code owns every action, target,
   required observation, authority field and bounded route. Invented workflows, invented
   evidence and omitted required evidence stop before routing.
2. **Independent verifier factory.** A trusted outcome contract compiles only when a separately
   sourced observation adapter is both independent from the acting driver and complete for every
   required observation. Raw observed state is omitted from receipts; unavailable, wrong or
   side-effect-bearing outcomes fail closed.
3. **Benchmark accounting.** Autonomous completion, precise handoff, incorrect side effects and
   silent false completion are counted separately. A development sample cannot become a 99.9%
   claim merely because its point estimate is perfect; the report includes a conservative
   binomial lower bound, a representativeness gate and a minimum all-success sample calculation.
4. **Reviewed database family.** A sixth explicit mode now supports one bounded experimental
   database action through a reviewed operation contract. It generates no arbitrary SQL, probes
   schema/procedure/input fitness without a business write, requires exact approval, reconciles
   before action or retry, independently reads state through a separate connection, resumes on
   proof, retains the capability and quarantines unknown or incorrect outcomes.
5. **Shared bundle factory.** All six enabled modes can now produce the same complete bundle
   and prepared-route shape without supplying a family manually. The mode encoded in the strict
   envelope determines the family, and the factory inserts independent-verification and
   reconciliation-before-retry invariants.

## Genuine disposable database route

The database checkpoint includes a real local SQLite customer world rather than only a mock:

- parameterized reviewed operation `create-reviewed-restock-draft`;
- pinned schema hash;
- allowlisted input keys and exact approval;
- duplicate-safe stable operation key;
- independent read-only verification connection;
- protected-state digest;
- simulated response loss after a genuine commit;
- reconciliation without a duplicate;
- fresh SDK instance retained reuse on a second operation;
- customer-local SQLite capability-registry persistence and retained reuse after a fresh
  registry process; and
- zero incorrect side effects in the passing route.

This is not general database support. It does not permit arbitrary SQL, table selection, schema
mutation, database discovery, customer credentials or production database access.

## Preserved limits and next dependencies

- The OpenAI planner adapter is implemented but has not been run or counted as model-backed
  universality evidence.
- Workflow selection is constrained to predeclared trusted customer workflows; arbitrary goal
  discovery across an unknown company is not proved.
- The verifier factory compiles trusted declarative outcome contracts; it does not yet invent a
  trustworthy verifier for an unknown system from nothing.
- Existing mode adapters can use the shared bundle factory, but their historical SDK result
  types have not all been rewritten to return bundles natively.
- Full customer packaging, ten-case database acceptance, drift handling and frozen model-backed
  transfer remain undone.
- The benchmark module measures a supplied case set; no representative universality corpus has
  yet been built, and no reliability claim is available.
- The high-risk residual-code sandbox remains disabled until its isolation, provenance,
  permission and verifier contracts exist.

The next safe phases are complete-bundle adapters for existing modes, durable database packaging
and acceptance, then the isolated trusted-tool/residual-code family. Higher-risk families must
not be enabled merely because their registry entries exist.
