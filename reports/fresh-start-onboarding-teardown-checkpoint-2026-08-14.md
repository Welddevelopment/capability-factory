# Fresh-start onboarding teardown checkpoint — 2026-08-14

## Result

The first zero-spend clean-package rehearsal reached
`acceptance-scaffold-ready`, executed the fixed ten-case fictional acceptance
package, persisted ten evidence receipts, reloaded both preparation and
acceptance state without extra attempts, and recorded zero surviving incorrect
effects.

This was an **automated author-independent packaging rehearsal**. It was not a
fresh-human onboarding study, a customer system, real-system acceptance,
production evidence, or proof of an under-one-day onboarding time.

## What was genuinely exercised

The participant path began only with the new fictional Northstar package in
`validation/fresh-start-onboarding-teardown-v1/package/`. It did not import the
repository's ERPNext, Gitea, Solstice, dispatch, procurement, browser, file,
inbox, or document helper fixtures.

The runner used fresh CLI processes to:

1. start a durable proposal-only onboarding session;
2. derive and write an exact digest-bound review artifact;
3. record the review and generate the fixed acceptance scaffold;
4. reopen the reviewed preparation from a new CLI process;
5. inspect the durable event history;
6. run the generic ten-case acceptance executor; and
7. reopen the completed acceptance campaign from a new durable store instance.

One measured run took 346.055 ms of machine wall-clock time, reaching the
preparation-ready state after 173.351 ms and acceptance completion after
345.603 ms. These timings measure local automation only. Human active time is
deliberately recorded as `null`.

## Measured inputs, confirmations, and generated artifacts

The fictional package explicitly supplied six categories of consequential
confirmation:

- the bounded workflow and exact operations;
- target and credential aliases;
- read/write authority, limits, forbidden actions, and retry policy;
- observable completion, duplicate, collateral-effect, and freshness rules;
- independence of the fictional observation binding; and
- the disposable reset and durable-state requirements.

Capability Factory automatically proposed the adapter inventory, verifier
contract, and authority compilation; calculated their exact review digests;
generated the review artifact; derived the ten-case plan; and preserved the
campaign state, per-case receipts, and external-state fixture files. The raw
machine-readable report is
`reports/fresh-start-onboarding-teardown-artifacts-2026-08-14/teardown-report.json`.

## Author-only work converted

| Former author-dependent step | Current disposition | Boundary |

## Exact remaining author/customer-specific gaps

1. **`customer-action-runtime-binding-not-generated`** — the factory records
   and digest-binds the action declaration, but it does not yet generate and
   qualify the executable customer-local action binding.
2. **`customer-observer-binding-not-generated`** — the factory proposes a
   verifier contract, but it does not yet generate and negative-control qualify
   the independently authenticated customer-specific observation adapter.
3. **`real-credential-and-environment-activation-missing`** — only the customer
   or workspace administrator can provide local credential aliases, disposable
   access, and the activation decision. Preparation grants no authority.
4. **`fresh-human-onboarding-evidence-not-run`** — a genuinely fresh platform
   engineer must use a frozen package before active time, questions, edits, or
   an under-one-day claim can be measured honestly.

The binding proxy was 33 nonblank declaration lines plus 76 nonblank
acceptance-fixture declaration lines. The rehearsal wrote **zero lines of real
customer executable binding code**. That is the key finding: command
orchestration and durable bookkeeping are no longer the dominant usability
gap; producing and qualifying the action and observation bindings without
author knowledge is.

## Claim boundary

The strongest supported statement from this checkpoint is:

> A clean fictional input package can now be carried through durable onboarding
> preparation, exact review binding, fixed acceptance execution, and durable
> reload without repository-specific helper fixtures.

It does **not** support saying that a new user can onboard independently, that
the adapter/verifier bindings are automatically generated, that a real system
was accepted, or that onboarding takes less than one working day.
