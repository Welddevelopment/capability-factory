# Capability Factory onboarding safety audit

Date: **2026-08-14**
Status: **deterministic local audit complete; no paid or model-backed execution**

## Purpose

This checkpoint independently re-audited the zero-spend onboarding foundation against the current product target:

> A normal product or platform engineer can connect Capability Factory to a supported documented system in less than one working day without manually building each missing integration.

That sentence remains a target, not a measured claim. This audit hardened the preparation path; it did not run a fresh-human comparison or activate a customer system.

## Existing joined foundation confirmed

The repository already contained a coherent, fail-closed onboarding path covering:

- approved local OpenAPI 3, MCP, and SDK/reference material;
- provenance-labelled adapter discovery;
- a provisional external-outcome verifier contract;
- an ordinary-language authority wizard;
- a framework-neutral, non-authorizing blocked-context contract;
- fixed ten-case acceptance-plan generation;
- a reusable constrained-HTTP Outcome Observer Factory;
- an assisted-onboarding console projection;
- a deterministic seven-case zero-spend benchmark; and
- a second frozen fictional HTTP system that had exercised the joined path through all ten acceptance cases.

## Safety issues found and fixed

### Adapter discovery

1. Swagger 2 and unsupported OpenAPI versions are now rejected rather than interpreted using OpenAPI 3 assumptions.
2. Provider-returned schema versions are revalidated at the provider-neutral boundary.
3. Provider evidence is bound to the exact approved input and material digest; forged provenance is rejected.
4. Trusted-fact and mandatory-blocker preservation applies to every provider, including locally labelled deterministic providers.
5. A same-target read operation remains only a reconciliation candidate. It cannot remove the `reconciliation-unproven` blocker until it is independently bound and verified.

### Verifier, authority, and acceptance

1. Provisional verifier contracts and authority compilations now contain intrinsic SHA-256 content digests.
2. Acceptance derivation verifies those intrinsic digests before trusting an outer review receipt. Mutating an artifact and recomputing only the caller-supplied review digest no longer legitimizes it.
3. The authority wizard rejects duplicate target aliases, credential aliases, read rules, write rules, and forbidden-action entries instead of silently normalizing ambiguous policy input.
4. Verifier intake rejects duplicate observer and observation-surface identifiers.
5. Executable outcome observers reject stale or implausibly future trusted operation-start boundaries, preventing an old observer binding from being reused as fresh evidence for a later action.

The blocked-context contract required no change. It already rejects secret-shaped data, oversized and unknown fields, duplicate context and authority references, any authority effect, and preserves separate delivery-request and durable-work identities.

## Strongest accurate current statements

The supported constrained-product statement remains:

> Inside a predefined trusted scope, Capability Factory can let an agent encounter a missing HTTP capability, construct it from trusted documentation, test it, use it within explicit authority, verify the external result, resume its original goal, and retain the capability.

The onboarding statement supported by this private checkpoint is:

> Given approved local OpenAPI 3, MCP, or SDK/reference metadata and a confirmed bounded workflow, Capability Factory can deterministically produce a provenance-bound, non-executable adapter proposal; scaffold and integrity-bind authority, verifier, and acceptance contracts; and identify the remaining customer and engineering blockers without granting write authority or treating generated tests as evidence.

The later frozen fictional HTTP checkpoint additionally supports that reusable observer primitives can sometimes remove handwritten verifier work and reach executable local acceptance. It does not establish arbitrary-system coverage or repeatable under-one-day onboarding.

## Work that still belongs to people

- The domain owner confirms the exact workflow, business success condition, and unacceptable collateral effects.
- The workspace administrator confirms targets, credentials aliases, reads, writes, approvals, limits, forbidden actions, and handoff owners.
- The platform engineer binds customer-local secret values, reviews consequential mappings, supplies unsupported runtime or observer code, connects the upstream agent, prepares disposable state, runs acceptance, and reviews evidence before activation.

## Exact remaining blockers to the under-one-day target

1. **Coverage outside reusable primitives.** OpenAPI `$ref` resolution, servers/base paths, callbacks, pagination, rate limits, richer error semantics, and some authentication lifecycles still need product support or engineering review.
2. **Independent observation gaps.** MCP and SDK metadata do not automatically provide an independently bound outcome observer. Some APIs expose no sufficient read surface, so customer-specific observer code or a different observation system remains necessary.
3. **Empirical setup time.** No fresh platform engineer has yet completed the frozen unfamiliar-system exercise without author help against a like-for-like manual integration baseline.
4. **Customer-specific activation.** Real workflow, sandbox, credentials, policy, security, operations, acceptance, contracting, and engagement gates remain separate and unresolved.
