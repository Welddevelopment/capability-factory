# CF-058 — Causally joined hardened HTTP acceptance

## Result

CF-058 completed one frozen, author-designed, fictional constrained-HTTP campaign through the joined product path:

`reviewed OpenAPI material → CF-036 work pack → CF-041/CF-051 source evidence → CF-053 production-derived candidate → CF-058 opaque causal bridge → pinned action/observer transports → independent workspace authority → short-lived write authority → generic mandatory acceptance executor`

The final v3 campaign passed all ten mandatory acceptance cases. It recorded seven intended business writes across isolated cases, one content-addressed candidate build, fresh-process retained reuse, one genuinely fresh-process interrupted-campaign reconciliation, zero surviving incorrect side effects, zero observer writes, zero blind retries, zero unresolved live authority leases, zero model calls and $0 spend.

This is stronger joined local evidence than the earlier component checkpoints. It is still one fictional local development candidate, not customer, production, arbitrary-API, independent held-out, public, universal-capability or CF–DAS integration evidence.

## What changed

### Exact causal bridge

`src/product/cf058-opaque-causal-http-bridge.ts` accepts only the opaque production-derived CF-053 candidate handle. It revalidates:

- the exact CF-036 work-pack digest already anchored by CF-053;
- the work pack's exact reviewed HTTP binding-factory result;
- all four reviewed action, no-write probe, reconciliation-readback and independent-observer method identities;
- target, scopes, stable identity and exact outcome predicates;
- separate action and observer credential boundaries.

The resulting bridge handle is module-private and required by the authority-enforced compiler wrapper. A cloned handle, development candidate, cross-factory work pack or conflated credential boundary fails closed.

### Separate approved observer API material

The HTTP binding factory now accepts an optional separately approved observer normalization. The existing one-document path is unchanged. When supplied, the observer is resolved only from that approved material and retains its own exact server URL and provenance receipt. This allowed CF-058 to exercise distinct TLS origins, certificates, credentials, routes and processes for action and observation without pretending both came from one OpenAPI origin.

### Durable production-candidate reopen

The first real run exposed that a new process could not safely recreate a CF-053 derived handle by repeating the earlier planning derivation. `reopenCf053DerivedContractFromDurableCandidate(...)` now reconstructs an opaque handle only after:

- finding exactly one integrity-valid content-addressed registry entry;
- re-hashing the retained action and observer source bytes;
- matching the exact persisted contract bytes;
- recomputing the trusted planning authority-context digest;
- validating the original workspace issuer root and public/private keypair;
- matching the issuer public-key digest already anchored in the contract.

It does not recreate planning state, mint a new trust root or accept a caller-supplied contract. Forged candidate digests, root mutation and retained contract mutation are covered by negative tests.

### Disposable customer-shaped processes

The campaign uses:

- one TLS 1.3 action-only child with a pinned leaf certificate and action credential;
- one different TLS 1.3 read-only observer child with a different pinned leaf certificate and credential;
- one fresh retained-candidate child;
- one fresh restart-reconciliation child;
- a shared integrity-wrapped fictional truth store, with no shared action route or credential.

The restart child reopens the exact interrupted generic campaign, resolves the current independently stored workspace activation, reconstructs the exact reviewed observer declaration and exact pinned observer transport, then observes external state without replaying the action.

## Ten acceptance cases

1. **Read-only success:** independently observed a pre-existing exact directive with no action or write.
2. **Approved write:** executed one bounded PUT and independently verified it.
3. **Fresh-process reuse:** reopened the exact registry candidate as retained in a new process, preserving build ordinal one.
4. **Missing credential:** stopped before dispatch with zero write.
5. **Missing permission:** revoked the exact live activation; the existing verifier rejected before network dispatch; a separately signed successor activation was required for later work.
6. **Lost response:** first replaced one expired, durably unconsumed lease generation; then used signed independent not-started evidence for one attempt-two reissue; a separate post-commit response loss was observed complete without replay.
7. **Wrong/partial outcome:** classified a pre-seeded partial state as partial with no CF write.
8. **Restart:** preserved the interrupted campaign after the write and completed reconciliation in a genuinely fresh process with no second write.
9. **Duplicate submission:** repeated exact work produced one external write.
10. **Conflicting stable-identity reuse:** changed input under the same stable identity was rejected before a second write.

## Exact boundary and next implication

CF-058 establishes that the currently hardened constrained-HTTP pieces can compose through one complete mandatory local acceptance campaign without weakening authority, recovery, independent observation or restart semantics. It does not establish that a fresh engineer can onboard a real provider quickly, that arbitrary documented APIs fit the subset, or that the system is production-ready.

The highest-value non-customer follow-up is no longer another renamed HTTP world. It is a fresh-author or automation study of the adapter/verifier setup burden, or a materially different documented API shape that attacks the declarative subset boundary. Customer-environment acceptance remains a separate gate.
