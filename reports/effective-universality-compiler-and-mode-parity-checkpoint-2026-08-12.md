## Capability Resolution Compiler

The compiler accepts model-compatible proposals containing only trusted keys and references.
Trusted local registries retain control over actions, targets, schemas, authority, approvals,
route builders, observation surfaces, verifier templates and aggregate completion.

Implemented rejection classes include:

- tenant, request, parent-goal or ordinary-goal identity change;
- unknown or disabled primitive;
- uncited or unauthorized evidence;
- cycles, missing dependencies and duplicate work-item identity;
- target, action, approval or risk escalation;
- missing route, observation or verifier implementation;
- write primitives without acceptable retry/idempotency semantics;
- missing, duplicate or extra bindings;
- unknown trusted values or artifacts;
- schema and classification mismatch;
- artifact flow without an explicit dependency; and
- terminal outputs not exactly covered by the trusted aggregate verifier.

The compiled plan is deterministically ordered, versioned and digest-bound to the primitive and
verifier registries. It is not yet wired into the live universal composition executor, and no
model-backed planner campaign was run.

## Verified artifact flow

The new customer-local SQLite artifact store permits publication only when:

- the producer has an independently verified passing receipt with zero incorrect side effects;
- the receipt digest, value digest and trusted schema agree;
- the artifact declares exact tenant, parent, plan, producer and allowed consumers;
- classification, expiry and schema boundaries are explicit; and
- the artifact ID has never been published before.

A downstream step can resolve the value only with the exact tenant, parent, compiled plan,
consumer work-item, schema and classification ceiling. The durable test reopened the store in a
fresh process and preserved the same bindings. This is local typed dataflow infrastructure, not
a distributed or encrypted production data plane; secret values are not supported artifacts.

## Runtime-family parity ladder

The new ladder separates:

1. `registered` — architectural slot only;
2. `bounded-loop` — complete bundle, ordinary goal, authority, pre-use and external verification,
   bad-result rejection and retained reuse;
3. `hardened-local` — reconciliation, duplicate safety, quarantine, restart, customer-local
   package and executed ten-case acceptance;
4. `transfer-local` — a second distinct system/contract plus a generic scaffold/factory; and
5. `onboarding-validated` — a genuinely fresh engineer completes onboarding without author help.

The ledger cannot record a demonstrated requirement without an evidence reference. A happy path
cannot skip the hardening level.

Current local assessment:

- authenticated browser: `transfer-local`;
- bounded file/EDI: `transfer-local`;
- signed message/inbox: below transfer-local;
- pinned document: below transfer-local;
- reviewed database: below transfer-local;
- pinned import-free WebAssembly tool: below transfer-local;
- signed agent/service delegation: below transfer-local.

No family has fresh-engineer onboarding validation. Only constrained HTTP retains the existing
working-local-pilot-MVP product maturity label; parity level does not silently change public
product maturity.
