CF-052 now joins the exact current progressive CF-051 boundary to one fresh fictional provider-task candidate for the existing strict declarative SDK subset. It rejects a reader, subclass, stale snapshot, retrospective import, different tenant, substituted semantic contract, changed work pack, stale method digest, or invalid source-review receipt.

For the supported subset, the compiler generates fixed separate action and observer JavaScript modules, hashes those exact bytes, loads those exact bytes as modules, and runs qualification through them. A module-owned launcher materializes two exact content-addressed process source files and starts two distinct real localhost children: an action process with the only write route and an observer process whose pinned source only reads the same durable fictional store. The launcher generates distinct random per-process nonces and tokens, verifies each child's actual PID, plane, endpoint, process-key digest and exact source bytes, then signs one launch receipt with a launcher-created ephemeral Ed25519 key. The compiler accepts only the original opaque handle present in its module-private `WeakMap`, revalidates that signed receipt, rereads both materialized source files, and challenges both token-protected children. A copied object, proxy, fake observer or caller-created two-port process cannot produce the required handle. The candidate is also bound to the exact integrity-checked CF-041 `reviewedContract`, exact persisted CF-036 work pack, a deep-frozen descriptor, and an Ed25519 public authority key identity. The qualification route exercised a no-write probe, one committed fictional action, direct reconciliation, a separately routed read-only observation of stored state, and a second identical action that returned `already-exists` without increasing the business-write count.

Freshness is compiler-derived rather than accepted as an observer boolean. The probe captures the durable provider's pre-action server sequence, any pre-existing record version and server timestamp, which becomes the operation-start baseline required by the exact persisted contract. The action advances the durable sequence and record timestamp. Reconciliation and the observer separately read the stable record ID, record version, timestamp and current server sequence. Crucially, the observer's judgment clock is solely `new Date()` inside the separate pinned observer child; it is never clamped to or advanced by provider state. CF-052 calls the result fresh only when the observed version is strictly newer than the bound baseline, the observed timestamp is not before operation start or in the future relative to that observer clock, its age at observation is no greater than the contract's exact `maximumAgeSeconds`, and it exactly agrees with the committed/reconciled record and timestamp. A bounded three-read catch-up handles only a measured clock skew of at most 25 ms; it never clamps either clock. The freshness receipt explicitly binds the reconciliation stable ID/version/timestamp/sequence, the exact window and baseline, and the exact inputs, observations and classifier results for all controls. A deliberately pre-existing stale record at version zero, a constructed newer-but-over-window observation and an actual future-dated record read through the real observer path all fail the same compiler predicate and cannot mint the freshness receipt.

The action entrypoint first accepts only bounded plain data, rejects proxies, accessors, symbols, serialization hooks and non-plain prototypes, and creates one deeply frozen snapshot. It hashes that snapshot, rechecks a signed typed authority receipt, and executes that same snapshot. The signature and receipt bind the exact candidate, exact input, tenant, scope, target, policy version, issue time, expiry, signer and current runtime clock. Cross-input reuse, expiry, a state-changing getter and proxy input all failed closed; the getter was never invoked.

The candidate state is deliberately named `qualified-local-candidate-not-accepted-not-activated`. Its descriptor says `customerExecutable: false`, `accepted: false`, and `activated: false`.

A second draft launched separate processes but accepted caller-supplied process identities, making observer independence self-attested; it is also superseded. The current result pins the persisted reviewed contract, launches exact process bytes behind an opaque module-private handle and signed launch receipt, rereads those materialized bytes before compilation, snapshots bounded plain input exactly once, and mints freshness evidence only from sequence/version/timestamp advancement that satisfies the exact operation-start and maximum-age contract against the observer child's own unclamped clock. No lost-response, restart recovery or replacement-process adoption is claimed by CF-052.
