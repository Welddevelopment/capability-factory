# Capability Factory under-one-day onboarding validation plan

Status: **prepared, not executed**

## Question

Can a competent product or platform engineer connect Capability Factory to a supported documented system in less than one working day without manually building each missing integration?

The test is about reduced integration work. It is not another test of whether the already working constrained-HTTP loop can execute in a familiar fixture.

## Frozen input package

The engineer receives only:

- Capability Factory’s packaged customer-local SDK or sidecar;
- one unfamiliar documented HTTP API and approved local documentation snapshot;
- sandbox credential aliases and separately delivered customer-local values;
- one representative blocked workflow;
- an explicit company authority policy expressed in ordinary language;
- an externally observable definition of completion and collateral constraints;
- installation and onboarding documentation available to any future pilot engineer.

The engineer must not receive a prebuilt customer adapter, hidden solution code, private author hints, or verifier implementation beyond reusable product patterns.

## Required completion state

The task is complete only when:

1. approved material is hash locked;
2. the proposed operation inventory is reviewed and confirmed;
3. credential values remain customer-local and absent from artifacts;
4. authority compiles from explicit answers and omitted authority fails closed;
5. an observation path independent from action execution is implemented;
6. the first missing capability is acquired and verified;
7. one approved external outcome is independently verified;
8. the original goal resumes;
9. fresh-process retained reuse works;
10. all ten mandatory acceptance cases execute with preserved artifacts and zero surviving incorrect side effects;
11. the setup remains blocked from activation until an explicit operator decision.

## Measurements

- elapsed time and active engineer time to first autonomous acquisition;
- time to full ten-case acceptance;
- lines and files of customer-specific code written;
- percentage of adapter fields proposed correctly;
- percentage confirmed without modification;
- verifier code and judgment still required;
- number and type of clarifying questions;
- manual interventions during acquisition and reuse;
- correct credential, permission, approval, partial, incorrect, and unknown stops;
- unsupported operations invented;
- unauthorized authority inferred;
- credential leakage or invention;
- time and code versus a manual bounded integration built from the same inputs.

## Precommitted failure rules

The run fails immediately if:

- any credential value appears in a proposal, log, evidence export, or model context;
- any write authority is inferred rather than explicitly confirmed;
- an unsupported operation is marked executable;
- the action response is treated as independent outcome proof;
- a partial, incorrect, stale, duplicate, collateral, or unknown result passes;
- a missing credential or permission causes a write attempt;
- a lost response causes a duplicate write;
- a declared test is reported as executed or passed without preserved evidence;
- the engineer requires hidden author assistance that a future pilot would not receive.

## Comparison design

Use the same engineer-skill band, API, workflow, sandbox, policy, and success contract for both routes:

- **Capability Factory route:** assisted discovery, authority, verifier, adapter and acceptance scaffolding plus the product runtime;
- **manual route:** normal documentation reading and a conventional bounded integration with equivalent safety and verification requirements.

Do not compare CF’s independently verified flow with an unsafe manual script that omits reconciliation or outcome checks. Record both a raw time comparison and a like-for-like safety-complete comparison.

## Repetition

The first result is developmental. A supportable under-one-day claim needs multiple fresh engineers and systems, including at least one ambiguous API and one case where a safe independent verifier cannot be generated automatically. Preserve failures and product changes chronologically; do not rewrite the first attempt after fixes.
